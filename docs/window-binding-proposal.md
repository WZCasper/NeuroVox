# Предложение: привязка области захвата к окну игры

**Статус:** предложение, не реализовано. Требует отдельного явного запроса
на реализацию — слишком велик риск сломать текущую рабочую схему координат
экрана, не покрытую автоматическими тестами на реальном Windows-окружении.

## Проблема

`config.Settings.rois` хранит абсолютные координаты экрана (`left, top,
width, height`), заданные один раз через `overlay.SelectionOverlay`.
`capture.ScreenCapture.grab(roi)` захватывает именно этот прямоугольник,
не зная и не интересуясь, какое окно там физически находится.

Из-за этого три бытовых действия игрока молча ломают распознавание:

- игрок подвинул окно игры (оконный/windowed-режим);
- игрок переключился на другой монитор (или у него их несколько, и игра
  открылась не на том, что ожидался);
- игрок сменил разрешение экрана или масштаб DPI.

Во всех трёх случаях рамка продолжает смотреть в прежние абсолютные
координаты, там уже не субтитры, а что-то другое (рабочий стол, другое
окно) — приложение просто перестаёт что-либо озвучивать. Диагностика из
пункта 3 этого списка задач («область N: субтитры не обнаруживаются N
секунд») смягчает последствие — пользователь хотя бы узнает, что что-то не
так, — но не устраняет причину и не может сама передвинуть рамку.

## Идея

Вместо (или в дополнение к) абсолютным координатам хранить **дескриптор
окна**, которому принадлежит рамка (заголовок и/или класс окна через
win32 API), и координаты области **относительно этого окна**, а не экрана.
Перед каждым захватом — находить текущее окно по дескриптору и пересчитывать
абсолютную область как `координаты_окна + относительный_сдвиг`.

## Что пришлось бы менять

- **`config.py`** — `Settings.rois` перестаёт быть списком
  `(left, top, width, height)`. Нужна либо новая параллельная структура
  (например, `window_title` + `roi_in_window` на каждую область), либо
  расширение текущей — с обязательной миграцией уже сохранённого
  `settings.json` у существующих пользователей (`Settings.load()` уже
  занимается восстановлением после повреждённого файла — сюда же
  естественно ложится и миграция старого формата на новый).
- **`overlay.py`** (`SelectionOverlay`) — после того как пользователь
  отпустил рамку (перетащил/изменил размер), нужно определить, над каким
  окном она оказалась, и посчитать координаты относительно этого окна.
  Разумная точка: `_on_change` (уже вызывается при каждом изменении
  геометрии) — но там понадобится опрос списка окон под курсором/под
  рамкой, а не только сохранение координат.
- **`capture.py`** (`ScreenCapture`) — перед `grab()` нужен новый шаг:
  найти окно по дескриптору (полный перебор `EnumWindows` либо
  `FindWindow` по заголовку/классу), получить его текущий `GetWindowRect`,
  прибавить относительный сдвиг. Если окно не найдено (игра закрыта,
  свёрнута) — это уже готовый, более точный источник для диагностики из
  пункта 3: не абстрактное «субтитры не обнаруживаются», а конкретное «окно
  игры не найдено».
- **`workers.py`** (`CaptureWorker`) — сам цикл захвата не меняется
  принципиально, но `grab(roi)` перестаёт быть чистой функцией от
  сохранённых координат: результат теперь зависит ещё и от текущего
  положения окна на экране, которое приходится узнавать заново на каждом
  кадре (или кэшировать на небольшое время, чтобы не дёргать `EnumWindows`
  с частотой `capture_fps`).
- **`gui.py`** — уместно показывать пользователю, к какому окну сейчас
  привязана область (заголовок в списке областей), и явно сообщать, когда
  окно потеряно.
- Новых внешних зависимостей, скорее всего, добавлять не придётся:
  `main.py` уже дёргает Win32 API напрямую через `ctypes.windll`
  (`_enable_dpi_awareness`) без `pywin32` — тем же способом (`ctypes.windll.user32.EnumWindows`,
  `GetWindowText`, `GetClassName`, `GetWindowRect`) можно получить всё
  необходимое для поиска и отслеживания окна.

## Риски и открытые вопросы

- **Несколько окон с одинаковым заголовком.** Два экземпляра одной игры,
  или заголовок вида `"Igra - Episode 3"`, меняющийся по ходу дела —
  поиск по точному совпадению текста заголовка ненадёжен. Потребуется
  запасной план: поиск по классу окна (обычно стабильнее заголовка) и/или
  явный выбор «это окно» пользователем в момент настройки рамки (кликнуть
  по окну игры), а не угадывание по тексту постфактум.
- **Полноэкранный режим (exclusive fullscreen) без рамки окна.** Классический
  полноэкранный режим у части движков вообще не создаёт обычное окно с
  заголовком в привычном смысле (либо создаёт, но `GetWindowRect` может
  возвращать не то, что реально видно на экране, — есть разница между
  `GetWindowRect` и `GetClientRect`, между экранными и клиентскими
  координатами). Для полноэкранных игр текущая схема (абсолютные
  координаты) может на практике оказаться даже надёжнее — тогда
  разумно не заменять её, а предложить пользователю выбор режима
  привязки («к окну» / «к экрану», как сейчас).
- **DPI-масштабирование.** В `main.py` уже есть комментарий именно про эту
  проблему: координаты расходятся на масштабе 125–150%, если приложение
  не DPI-aware. Здесь та же ловушка проявится ещё раз, но уже по
  отношению к окну игры (у которого может быть свой DPI-контекст,
  отличный от того, где рисуется оверлей), и её придётся решать заново.
- **Окно свёрнуто или временно не существует.** `EnumWindows`/`FindWindow`
  на устройстве пользователя без гарантии, что окно вообще ещё есть
  (игра закрыта, свёрнута в трей, идёт загрузочный экран без основного
  окна). Нужно аккуратное поведение при «окно не найдено»: не падать,
  не спамить ошибками на каждый кадр, дать пользователю понятный статус.
- **Обратная совместимость.** Существующие пользователи с уже настроенными
  `rois` в `settings.json` должны либо продолжить работать по старой схеме
  (абсолютные координаты как вариант по умолчанию), либо получить
  ненавязчивую миграцию/повторную настройку, а не молча сломанные рамки
  после обновления.

## Ориентировочный объём работы

Учитывая, что новых зависимостей не требуется (win32-вызовы через уже
используемый в проекте `ctypes.windll`), но требуется аккуратная работа
с сериализацией настроек, миграцией и UI:

- Поиск/отслеживание окна через `ctypes` + пересчёт координат в
  `ScreenCapture`: небольшая, локализованная задача.
- Изменения в `Settings` (новый формат `rois`, миграция старого
  `settings.json`) и в `overlay.py` (определение окна под рамкой): основной
  объём работы, требует аккуратности из-за обратной совместимости.
- Обработка перечисленных выше рисков (несколько одинаковых заголовков,
  полноэкранный режим, потеря окна) и связанный с этим UX в `gui.py`:
  по объёму сопоставима с предыдущим пунктом, но именно здесь спрятана
  основная неопределённость — сколько ручной доводки под конкретные игры
  потребуется, заранее не известно без тестирования на реальных играх в
  реальном Windows-окружении (эта среда разработки — Linux-контейнер без
  доступа к Win32 API, реальному экрану и реальным окнам, поэтому здесь
  возможна только архитектурная оценка, а не практическая проверка).

Суммарно — заметно больше, чем любая из остальных задач этого списка:
это не точечное исправление, а изменение модели данных (`Settings.rois`)
и добавление нового класса отказов (окно не найдено, окно неоднозначно),
которые нужно продумать и протестировать на реальных играх, а не только
на синтетических данных.
